# Antigravity и Qriterra: воспроизведение, исправления, проверка

Дата: 2 октября 2026 года. Объект проверки: Agent Shuttle и отдельный репозиторий Qriterra (`agent-code-checker`). Модель обзора: `gemini-3.8-flash-high`, effort `high`.

## Почему запуск повторялся с ошибкой

`agy.exe` был установлен и авторизован в обычном сеансе Windows. Дочерний процесс, запущенный из ограниченного командного процесса Codex, не мог читать и писать `%USERPROFILE%\.gemini\antigravity-cli`. CLI сообщал одновременно `Access is denied` и `You are not logged into Antigravity`. Из ограниченного окружения ошибка воспроизведена 3 раза из 3 без модельных запросов (`.runtime/agy-auth-sandbox-reproduction.json`). Команда `agy models` в обычном пользовательском сеансе успешно вернула каталог моделей.

До исправления A2A-сервер мог объявить `/bridge/identity` готовым, а первый настоящий запрос падал на доступе к профилю CLI. Регрессионный тест сначала показал этот разрыв пять раз подряд. Теперь Antigravity-сервер до открытия порта проверяет `agy models`. Ошибка авторизации прерывает запуск с явным диагностическим сообщением. Упреждающая проверка может длиться до 45 секунд, поэтому ожидание готовности временного сервера Antigravity увеличено с 30 до 60 секунд; отдельный тест воспроизводит позднюю, но успешную готовность.

После исправлений два последовательных запроса метаданных Antigravity через пользовательский Bridge успешно запустились и вернули ответ (2 из 2). Они не отправляли модельных задач.

Эта проверка не меняет права процесса. Для вызовов из ограниченного клиента Antigravity-сервер нужно запускать в авторизованном пользовательском сеансе и затем подключаться к нему. Пример команды приведён в [руководстве запуска](getting-started.md).

## Исправления Qriterra, обнаруженные во время живого запуска

- Проектный обзор Antigravity теперь по умолчанию запрашивает проверяемую политику `read_only`; `full_access` доступен только при явном выборе и разрешении сервера.
- Лимит отдельного хода Antigravity получает проектный лимит Qriterra. Прежние 300 секунд оборвали третий пакет при общем лимите 1800 секунд и закрыли сессию.
- Запрос на исправление ответа сохраняет проектную схему `2.0` и позволяет агенту читать исходники для сверки цитат. Раньше он требовал схему `1.0` и запрещал чтение.
- Если после исправления один результат пакета остаётся неверным, Qriterra сохраняет другие результаты только после самостоятельной полной проверки каждого правила, включая путь, строки и точный фрагмент исходника. Неверные правила остаются ошибками. Проектные промпты явно описывают обязательные типы и поля JSON.
- Отладочный отчёт сохраняет нативный ID беседы Antigravity и счётчики токенов ответов.

## Живая проверка одной беседы

Первый запуск Qriterra был выполнен из обычного пользовательского процесса. После его остановки продолжение подняло новый CLI-процесс с `--conversation 48003d7a-46f2-41df-b710-6785462d04c0`. Перед модельной работой новая политика `read_only` отклонила пробную запись файла; последующее чтение файлов разрешено. Все завершившиеся ответы обоих запусков, в которых CLI сообщил ID беседы, содержат тот же ID. Код прекращает продолжение, если CLI сообщает иной ID.

| Артефакт | Итог |
| --- | --- |
| `.runtime/qriterra-gemini38-report.json` | Первый запуск: 80 ошибок правил после неверной схемы исправления и тайм-аута. |
| `.runtime/qriterra-gemini38-resumed-report.json` | Продолжение той же беседы: 1 правило прошло, 10 обнаружили запах, 69 завершились ошибкой формата; лимит 3600 секунд исчерпан. |
| `.runtime/qriterra-gemini38-recovered-report.json` | Повторная проверка сохранённых ответов **без новых модельных вызовов**: 12 правил прошли, 10 обнаружили запах, 58 остались ошибками. Проверено 22 из 80 правил (27,5%). |

Оценка качества проекта не вычислена: строгое покрытие неполное. Десять подтверждённых валидатором находок относятся к первой группе эвристик качества кода, например длине методов, длинным спискам параметров и дублированию. Их инженерную значимость нужно оценивать отдельно; валидная цитата подтверждает расположение кода, а не автоматически приоритет переработки.

Два запуска отправили 37 запросов к агенту, включая исправления ответов. Отчёты CLI суммарно содержат `3 623 464` total tokens (`3 068 890` input, `554 574` output) и `44 042 303` cache-read tokens. Сравнения с несколькими независимыми беседами нет, поэтому денежную или токеновую экономию **не подтверждаем**. Одну нативную беседу проверили по ID; большой расход при повторных длинных ходах показывает, что само по себе это условие не ограничивает затраты.

## Тесты и структура

Тесты писались до соответствующих изменений и сначала воспроизводили отказ: пять повторов ошибочной готовности сервера, ожидание поздней готовности, лимит хода 300 секунд, несовпадение ID беседы, ошибочную схему исправления и потерю валидного соседнего результата пакета. Qriterra: **73 теста прошли**. Agent Shuttle: **264 теста прошли, 8 пропущены**. Полный вывод Agent Shuttle сохранён в `.runtime/final-suite.log`.

Примечание об изменении 3 октября: Agent Shuttle перешёл на один пакет `src/agent_shuttle/`; совместимый пакет `agent_bridge/` и старые команды удалены в версии 0.6. Qriterra остаётся отдельным репозиторием. Фактические задачи и сессии A2A обслуживает `TaskManager`; старый `SessionManager` не используется маршрутом A2A.
