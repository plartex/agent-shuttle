# Обнаружение и подключение Agent Shuttle

Agent Shuttle — **Python-библиотека и MCP-сервер** для делегирования исследований, ревью, реализации и получения второго мнения у локальных Antigravity, Codex, Claude Code, OpenCode и настроенных ACP-агентов. A2A — протокол взаимодействия с агентами. Доступность веба и других средств исследования определяется выбранной средой и политикой.

## Python API

Установите `uv add agent-shuttle` в своём Python-проекте. Используйте `TaskManager`, `ShuttleClient` или `connect_harness`. MCP-клиент для работы библиотеки не нужен. См. [справочник API](api.md).

## MCP

Установите `uv tool install agent-shuttle`. Команды `agent-shuttle mcp` и `agent-shuttle-mcp` запускают одинаковый stdio-сервер. Сам факт установки не подключает клиент.

```text
agent-shuttle mcp setup --format codex-toml --config PATH_TO_CONFIG_TOML --workspace ABSOLUTE_PROJECT_PATH
agent-shuttle mcp setup --format codex-toml --config PATH_TO_CONFIG_TOML --workspace ABSOLUTE_PROJECT_PATH --apply
agent-shuttle mcp doctor --format codex-toml --config PATH_TO_CONFIG_TOML --json
```

Для конфигурации JSON с секцией `mcpServers` выберите `--format mcp-json`. Укажите фактический конфигурационный файл клиента. Без `--apply` команда показывает предпросмотр. При применении она сохраняет чужие настройки и TOML-комментарии, делает резервную копию и откатывает собственные изменения при неудачной проверке подключения. Повторное применение без изменений не создаёт ещё одну копию. После изменений перезагрузите подключение в клиенте.

Диагностика MCP проверяет handshake, версию и инструменты. `list_agents` показывает агентские ID и наличие команд без запуска агентов. Авторизация при этом не проверяется. `get_agent_info` запрашивает живые модели, квоты и гарантии политик. `agent-shuttle doctor AGENT_ID --smoke` отдельно запускает проверочный модельный ход.

## Docker Gateway

Версия 0.8 проверена с Docker MCP 0.44.1. В конфигурации MCP-клиента укажите абсолютный путь к установленной команде `agent-shuttle` и аргументы `mcp gateway --profile default --workspace ABSOLUTE_PROJECT_PATH`.

Адаптер объединяет два локальных stdio-подключения: настоящий Docker Gateway с выбранным профилем и Shuttle. Поиск `mcp-find` включает описание Shuttle; его инструменты вызываются напрямую или через `mcp-exec`. Вызовы Docker-инструментов передаются исходному Gateway с сохранением его политик. Профиль и настройки безопасности Docker не изменяются. Shuttle работает на хосте и не находится в контейнерной песочнице Docker; ограничения задач обеспечиваются выбранной агентской средой.

Ищите по словам `Antigravity`, `Codex`, `delegate`, `research`, `review`, `делегирование`, `исследование`. Затем используйте `list_agents`, `get_agent_info`, `ask_agent` или `submit_task`. Docker `code-mode` объединяет только Docker-инструменты. `mcp-add` и `mcp-remove` включают и отключают Shuttle в текущей сессии адаптера. Совпадения имён инструментов отклоняются.

Docker 0.44.1 по умолчанию запрещает remote URL на loopback и обычный HTTP. Поэтому локальное подключение использует stdio. Отдельный HTTP-режим `agent-shuttle-mcp --transport streamable-http --port 8769` предназначен для прямых клиентов: требуется случайный `AGENT_SHUTTLE_MCP_TOKEN` длиной от 32 символов и заголовок `Authorization: Bearer TOKEN`; сервер слушает только `127.0.0.1` и проверяет Host/Origin.

Дочерний worker получает собственный stdio-сервер с запретом вложенного делегирования. Транспортные токены не наследуются агентскими процессами.

## Политики веб-исследования и полного доступа

Для веб-исследования через встроенный Antigravity укажите `tool_policy="web_research"` в `ask_agent` или `submit_task`. Этот режим разрешает только нативные `search_web`, `read_url_content` для HTTP(S) и `view_content_chunk`. Локальные файловые инструменты, shell, произвольные MCP-вызовы и субагенты запрещены. Это ограничение инструментов, а не сетевая или процессная песочница. `read_only` по-прежнему означает чтение локальных файлов проекта и не разрешает веб-поиск. Другие harness и профили не получают `web_research` автоматически; проверяйте `get_agent_info`.

Вызов MCP с `tool_policy="full_access"` поддерживается для Codex и встроенного Antigravity. Для Antigravity менеджер запускает отдельный сервер с `--agy-dangerously-skip-permissions`, не переиспользуя ограниченный сервер. Обычный `get_agent_info` может не рекламировать `full_access`, пока сервер запущен без этого флага. Неограниченные инструменты требуют явного разрешения пользователя; MCP-параметр сам по себе не проверяет наличие такого разрешения. Автоматически заменять ограниченную политику на `full_access` нельзя.

Результаты Antigravity содержат `details.tool_policy` и `details.tool_policy_audit`: имена инструментов, решения и коды без содержимого запросов или страниц. Отрицательная проверка разрешений перед задачей в аудит результата не включается.

Явный запуск `python tests/web_research_mcp_smoke.py REPORT.json` проверяет настоящий вызов stdio MCP, веб-поиск и чтение страницы. Этот opt-in тест использует существующую авторизацию Antigravity и квоту модели, не задаёт модель и работает во временной папке. Он не входит в офлайн-набор.

## Выпуск и приёмка

`server.json` описывает публичную запись `io.github.plartex/agent-shuttle` и запуск версионированного PyPI-пакета через `uvx agent-shuttle@VERSION mcp`. README содержит соответствующий маркер владельца. Подготовка манифеста сама по себе ничего не публикует.

Проверьте тесты, сборку, официальную JSON Schema и чистую установку. После разрешения на публикацию выпустите проверенный пакет в PyPI, опубликуйте манифест официальным MCP publisher и прочитайте запись обратно. Доступность публичного реестра и поиск в конкретном Docker-каталоге проверяются отдельно.

Корпус `tests/fixtures/discovery_queries.json` содержит 16 положительных и 8 отрицательных запросов RU/EN. `python tests/evaluate_discovery.py --output REPORT.json` проверяет выбор по схемам в независимых модельных ходах Antigravity с принудительным `no_tools`. Это отдельная проверка выбора инструмента, которая расходует квоту; реальное выполнение проверяет сквозной Docker-тест с тестовым агентом. Проверка холодного чата после публикации остаётся отдельным этапом приёмки.

См. [выбор установленного harness](getting-started.md#выбор-установленного-harness).
